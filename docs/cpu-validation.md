# CPU 部署验证记录

验证日期：2026-10-29。本文记录发布前的本地实现验证，未替换现有业务部署。0.1.3 没有 `0.1.3-cpu` 标签；0.1.4 的正式镜像、匿名拉取和部署结果以对应 Release 及 Actions 记录为准。

## 环境与依赖

- Linux amd64 容器，Xeon E5-2698B v3，Docker 分配 10 个逻辑核心、约 31.3 GiB 内存；原生线程 2、CPU 工作线程 4。
- CPU 镜像通过本轮 Dockerfile 真实构建；构建时使用临时下载缓存和 PyPI 镜像加速，默认软件源仍为官方地址，未改变宿主机的包源配置。
- 主环境、RF-DETR 环境及本地 OCR 环境均为 `torch 2.6.0+cpu`，CUDA 版本为空；Paddle 3.2.0 未编译 CUDA，没有 NVIDIA、GPU Paddle 或 GPU ONNX Runtime 包。
- 推理容器未请求 GPU，未挂载 GPU 设备，网络仅连接独立测试数据库；模型缓存只读，不允许补下载。未访问业务数据库、未调用云端 OCR 或付费翻译。

模型测试使用一张 1280×1807 样本：检测、一个文本裁图的 OCR 分别执行；蒙版、修复、排版使用样本已保存的 16 个区域和译文，另直接运行 CTD 与 LaMa 验证推理。它验证默认组件能在 CPU 镜像中工作，不代表整本 OCR／翻译质量或所有可选 OCR 模型均已实测。耗时包含冷启动，不作为性能基准；CPU／GPU 的 10 页对照及限制见[部署指南](agent-deployment.md)。

模式切换修复另在 CPU 验证镜像中只读挂载修复后的后端代码进行离线探针验证：保存 `auto` 或 `cuda:0` 时，实际设备均为 CPU，就绪状态通过且 MCP 无设备阻塞。该探针没有运行模型推理；正式版本由发布流程重新构建并验证。

## 镜像体积

两项均不含挂载的模型权重和漫画数据。GPU 对照为本机已有的 0.1.3 验证镜像。

| 测量方式 | CPU 镜像 | GPU 对照镜像 |
| --- | ---: | ---: |
| 当前 Docker 引擎报告的 `.Size` 内容字节 | 1,165,357,839（约 1.17 GB） | 6,184,361,185（约 6.18 GB） |
| 无数据挂载容器中 `du -sx --block-size=1 /` | 4,001,464,320（约 4.00 GB） | 12,414,980,096（约 12.41 GB） |

Docker 的内容大小与解包后的文件占用不同，不能把其中一个当成另一个。实际网络拉取量由正式镜像、平台和已有缓存决定。以上为本地验证镜像的测量；正式发布会另行验证 GHCR 匿名拉取，不能以本地镜像测试代替。
