## CPU 部署与 Agent 硬件检查

- 新增独立 Linux amd64 CPU 后端镜像，保留 RF-DETR、PaddleOCR-VL 1.6、CTD、LaMa、Pillow 及漫画包／PDF 导入，使用 CPU PyTorch 和独立模型运行环境。
- `MANGAFLOW_RUNTIME=gpu|cpu` 明确选择运行模式，默认 GPU。CPU 模式不请求 GPU，关闭 CUDA，使用 OpenCV 分割；数据库、资产、端口和云端配置继续保留。
- 修复原模型配置指定 `cuda:0` 时切换 CPU 后被网页与 MCP 就绪检查阻塞的问题。运行时按 CPU 执行，原设备偏好保留，切回 GPU 并重建服务后恢复使用。
- 新增官方部署 Skill、硬件检查指南和可复制提示词。Agent 先检查实际部署目标；无可用 NVIDIA GPU 时说明性能影响，用户明确接受后才继续 CPU 部署。
- 发布流程验证 GPU 后端、CPU 后端及共享前端的摘要、匿名拉取、非默认端口、MCP 与持久化，全部通过后更新稳定标签并发布部署包。

## 升级到 0.1.4

1. 备份 PostgreSQL 数据库、`data/`、`.env`、`config.yaml` 和密钥。
2. 下载本 Release 的 `mangaflow-docker-0.1.4.zip`，将 `docker-compose.yml`、`docker-compose.cpu.yml` 和 `scripts/` 合并到原部署目录。保留私有配置、数据、模型目录及数据库卷。
3. 在原 `.env` 设置 `MANGAFLOW_IMAGE_TAG=0.1.4`，并按实际硬件设置 `MANGAFLOW_RUNTIME=gpu` 或 `MANGAFLOW_RUNTIME=cpu`。保留原模型和云端配置。
4. 在原目录执行：

   ```bash
   bash scripts/docker.sh pull
   bash scripts/docker.sh up -d
   bash scripts/docker.sh ps
   ```

仅执行 `restart` 不会应用新镜像和环境。CPU 模式需要 Compose 2.30+，不需要 NVIDIA 驱动；GPU 模式仍需 NVIDIA GPU、兼容驱动及容器透传。首次模型下载另需时间，翻译服务仍需配置。现有 0.1.3 没有 CPU 镜像，不要使用 `0.1.3-cpu`。

## 镜像与验收边界

- GPU 后端：`ghcr.io/alittlepandaman/mangaflow-backend:0.1.4`。
- CPU 后端：`ghcr.io/alittlepandaman/mangaflow-backend:0.1.4-cpu`。
- 共用前端：`ghcr.io/alittlepandaman/mangaflow-frontend:0.1.4`。
- 部署 ZIP 及 SHA-256 校验文件。模型权重独立下载和缓存。

无 NVIDIA GPU 时不推荐本地批量处理。Xeon E5-2698B v3／V100 16GB 的 10 页对照中，不含 OCR 与翻译，CPU 约 12 分 38 秒，GPU 约 2 分 7 秒；不是其他硬件的固定耗时。云端 OCR 可以减少本地识字负担，检测、蒙版和修复仍会占用 CPU。

本地已验证默认 CPU 模型样本、导入导出、HTTP／stdio、持久化和模式切换；发布 smoke 检查服务与协议，不代替整本漫画的 OCR、翻译或视觉质量验收。实际范围见仓库的 CPU 验证记录。本版本不新增数据库迁移或 MCP 工具，连接程序仍为 2.1.1。
